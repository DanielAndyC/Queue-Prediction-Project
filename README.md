## 1. What This Project Does

The project answers one question:

> Can class schedule data and building walking times predict the queue length
> at the CYM canteen, and where is the actual bottleneck?

To answer it, the project:

1. Builds a discrete-event simulation of the CYM canteen queue.
2. Drives the simulation with **real HKU class counts** (from the CYM lunch and
   dinner counts PDF) and **real walking times/distances** from nine HKU
   buildings to the canteen.
3. Engineers features that link class schedules and building locations to queue
   length.
4. Trains regression models to predict queue length.
5. Validates predictions using cross-correlation and sensitivity analysis.
6. Identifies the bottleneck in the two-stage queue structure.

The CYM canteen is modelled as a **two-stage queue**:

- **Stage 1 — Ordering kiosks.** Students queue at one of six ordering/payment
  kiosks. Drinks are picked up at the same kiosk, so there is no separate
  drinks station.
- **Stage 2 — Food counters.** After ordering, students queue at one of four
  food counters — **Supreme BBQ**, **China Kitchen**, **Noodle Spot**, and
  **Gourmet Kitchen** — each staffed by three parallel servers.

---

## 2. Project Type

**Hybrid (simulation/modelling + data analysis).**

- *Simulation/modelling:* a SimPy discrete-event simulation generates
  queue-length data under different scenarios. Mathematical queueing
  relationships (arrival rate vs. service capacity) drive the model.
- *Data analysis:* pandas and scikit-learn are used to fit distributions,
  engineer features, train regression models, and evaluate accuracy.

A machine learning prediction component is included as part of the data
analysis, but the main type is simulation + data analysis.

## 5. How to Run

From the project root, with the virtual environment activated:

```bash
python main.py
```

This runs the full pipeline in order:

1. **Simulation** — generates queue data for 30 days across both meals and
   saves each student's journey through the two-stage queue.
2. **Feature engineering** — builds the combined feature table from those
   saved student arrivals and the queue logs.
3. **Exploration** — prints queue statistics.
4. **Model training** — runs four experiments and prints MAE/RMSE.
5. **Analysis** — cross-correlation and sensitivity analysis.
6. **Visualisation** — saves plots to `data/`.

If you want to run a single step:

```bash
python src/simulation.py
python src/features.py
python src/data_analysis.py
python src/model.py
python src/analysis.py
python src/visualise.py
```

## 6. Data Sources and Assumptions

### 6.1 Real data used

- **Class counts:** HKU CYM lunch and dinner counts by weekday. Each distinct
  class arrangement is counted once per semester and weekday. From the HKU CYM PDF, it notes
  that hour labels use 10:50 / 11:50 / 12:50 and 16:50 / 17:50 / 18:50 as
  cutoffs, so a class labelled "12:00" actually ends at 11:50.
- **Per-building class counts:** the CSV records the number of classes ending in each hour for each building.
  This makes the location dimension of the simulation fully empirical rather than probabilistic.
- **Canteen layout and counter names:** from direct on-site observation.
  Four counters (Supreme BBQ, China Kitchen, Noodle Spot, Gourmet Kitchen),
  each staffed by three parallel servers, plus six ordering kiosks arranged
  as a single pooled FCFS queue.
- **Walking times and distances** from nine HKU buildings to the CYM canteen:

  | Building | Walk time | Distance |
  |----------|-----------|----------|
  | CYM Phys | 1 min | 30 m |
  | Meng Wah Complex | 1 min | 50 m |
  | Runme Shaw | 2 min | 130 m |
  | Run Run Shaw | 3 min | 180 m |
  | KK Leung | 4 min | 150 m |
  | Knowles | 4 min | 170 m |
  | James Hsioung Lee | 4 min | 240 m |
  | CYM Chem | 9 min | 500 m |
  | Rayson Huang Theatre | 12 min | 750 m |

### 6.2 Assumptions

Because some data is not publicly available, the project assumes:

- **Average class size:** 50 students (log-normal distribution, log-space SD 0.8).
- **CYM attendance fraction:** 10% of each class walks to the CYM canteen. The
  number of attendees is drawn from a binomial distribution
  `Binomial(n=class_size, p=0.10)`, so some classes contribute zero students
  while others contribute more than the average. This parameter is tuned so
  that the simulated peak queue matches the observed peak.
- **Balking:** if the kiosk queue exceeds `BALK_THRESHOLD` (currently 25), a
  fraction `BALK_PROBABILITY` (currently 50%) of arriving students walk away
  without joining. This reflects realistic canteen behaviour where students
  avoid very long queues.
- **Building assignment:** read directly from `data/real_class_counts.csv`.
  Each class is assigned to its actual building, and the
  walking time is looked up from the `BUILDINGS` table in  `config.py`.
- **Arrival spread:** each class produces arrivals centred on
  `class_end + walking_time`, with Gaussian noise (SD 10 minutes) representing
  students who leave class at different times.
- **Service times:** Gaussian, with means set to observed values. Kiosk mean
  1.5 min; China Kitchen 1.5 min; Noodle Spot 2.0 min; Supreme BBQ 3.0 min;
  Gourmet Kitchen 3.5 min.
- **Counter popularity (lunch):** Supreme BBQ 40%, Gourmet Kitchen 35%,
  Noodle Spot 15%, China Kitchen 10%.
- **Counter popularity (dinner):** Supreme BBQ 45%, Gourmet Kitchen 25%,
  Noodle Spot 15%, China Kitchen 15%.
- **Random seed:** All randomness is controlled by `BASE_SEED` in `config.py`.
  Changing it will produce different queue data, different feature values,
  and slightly different MAE results. The default is 42.

### 6.3 What is simulated, not real

- **Class sizes** are sampled from a distribution, not from enrolment records.
- **Building assignment** is read directly from the CSV, not from actual timetables.
- **Weather, holidays, and exam periods** are not modelled.
- **Class-schedule conflicts** (two classes ending at the same time) are not
  modelled beyond the natural aggregation of arrivals.

## 7. Key Results

Results are stable across reruns. Numbers below are from a representative run
using the current class counts and calibrated parameters.

### 7.1 Aggregate simulation results

| Metric | Value |
|--------|-------|
| Mean queue (all) | 12.0 |
| Lunch mean | 15.4 |
| Dinner mean | 8.6 |
| Peak queue | 95 (day 28, Thursday lunch, at 13:03) |
| Students served per meal | 200–400 |
| Cross-correlation peak | +18 minutes |

### 7.2 Model performance (Decision Tree, depth 7)

| Experiment | MAE | Baseline MAE | Error reduction |
|------------|-----|--------------|-----------------|
| A: Schedule-only, predict current queue | 3.59 | 14.62 | ~75.4% |
| B: Predict queue 10 minutes ahead | 3.43 | 14.87 | ~76.9% |
| C: Predict change in queue length | 0.74 | 0.90 | ~18.2% |
| D: All features (including lag) | 0.80 | 14.62 | ~94.6% |

**Experiment A is the key result.** With no queue history at all, schedule and
location features alone reduce prediction error by three quarters. This is
direct evidence that the location-and-time approach works.

**Experiment B is comparable.** Forecasting 10 minutes ahead gives a similar
MAE (3.43) to predicting the current minute (3.59). The queue memory is long
enough that future values are predictable from schedule features.

**Experiment C is positive but modest.** One-minute queue changes are
dominated by stochastic noise. The depth-7 tree reduces error by 18.2%
relative to the mean baseline, showing that even rapid fluctuations carry some
predictable structure.

### 7.3 Why Experiment D alone is not enough

The lag feature (`queue_length_lag1`) dominates feature importance in
Experiment D, so the model is effectively doing persistence forecasting
("the queue now is roughly the queue one minute ago") rather than using the
schedule. Experiment A (schedule-only) and Experiment C (predict change)
isolate the schedule's contribution and show it is substantial.

### 7.4 Cross-correlation

Strongest positive correlation at lag **+18 minutes** (r = 0.57). The queue
length responds to arrival bursts over the following 15–20 minutes, consistent
with the physical lag between class end, walking time, kiosk service, and
counter accumulation. The wide arrival spread (SD 10 minutes) means the
effective arrival curve is smoother than a single burst, which pushes the
cross-correlation peak later than the walking-time-only expectation.

### 7.5 Bottleneck identification

The **stage-wait plots** show the mean wait at kiosks vs counters over 30 days:

- Kiosk wait (Stage 1): **1–4 minutes** on most days
- Counter wait (Stage 2): **5–16 minutes** on most days

**The counters are the bottleneck — not the kiosks.**

### 7.6 Sensitivity analysis (averaged over 5 seeds, lunch)

| Scenario | Mean | Peak |
|----------|------|------|
| Baseline | 10.78 | 44.40 |
| 7 kiosks | 10.60 | 43.00 |
| 5 kiosks | 9.37 | 39.40 |
| Faster kiosk service (0.67×) | 10.07 | 38.60 |
| Slower kiosk service (1.33×) | 9.49 | 39.60 |
| Faster counters (0.7×) | **4.10** | **31.20** |
| Slower counters (1.3×) | **27.83** | **72.00** |
| Students walk 2× faster | 9.21 | 41.80 |
| Students walk 2× slower | 10.83 | 44.00 |

**Findings:** Counter service speed dominates queue magnitude. Halving counter
service time reduces the mean queue by ~62%; slowing it by 30% increases the
mean queue by ~158%. Kiosk capacity barely affects the queue — going from 6
to 7 kiosks changes the mean queue by less than 2%. Walking speed shifts
arrival timing but does not change the total number of arrivals. Averaging
over five seeds removes single-run noise and makes every row behave as
queueing theory predicts.

**The key operational insight:** adding kiosks is not effective. The effective
lever is counter throughput — either more servers or faster service at the
food counters.

### 7.7 Feature importance (Decision Tree, schedule-only)

| Feature | Importance |
|---------|------------|
| `students_arrived_last_30min` | 0.74 |
| `students_arrived_last_60min` | 0.18 |
| `students_arrived_last_15min` | 0.03 |
| `minute_of_day` | 0.02 |
| `total_classes` | 0.02 |

The 30-minute arrival window dominates, consistent with a slow-drain system:
the queue reflects arrivals over the past half hour, not just the
instantaneous arrival rate.

## 10. Limitations

### 10.1 Limitations

- Queue data is **simulated**, not observed from the real canteen. The model is
  calibrated against a small number of on-site observations (two lunchtime
  sessions).
- Class sizes are sampled from an assumed distribution, not from enrolment records.
- Building assignment is read directly from the CSV, not derived from actual timetables.
- Walking times are fixed per building; real walking times vary by individual.
- **Single-burst arrival model.** Each class produces arrivals within a
  Gaussian window centred on `class_end + walking_time`. Reality has a longer
  (~20–30 minute) tail, so the model's queue peak is slightly earlier and
  sharper than observed.
- The simulation models balking (students leave if the kiosk queue is too
  long) but not counter-level balking, and not reneging (students who have
  joined and then give up after waiting).
- The simulation does not model staff or visitor demand — only students from
  the scheduled classes.
- No causal claims: the model estimates associations between schedule patterns
  and queue length; it does not prove that changing the schedule would
  produce the predicted effect in the real world.

### 10.2 What the project can and cannot claim

**Can claim:**
- The method works: schedule features alone reduce prediction error by
  roughly three quarters in the simulation.
- The simulation is calibrated to real HKU class counts, real walking times,
  and on-site observations of queue magnitudes.
- The two-stage structure is correct: the counters are the bottleneck, not
  the kiosks.
- The pipeline is transferable: given real queue data, the same approach
  would apply.

**Cannot claim:**
- Real canteen queue accuracy at exact timestamps.
- Student-level precision, because class sizes are assumed.
- A validated schedule-change proposal — only a what-if engine.

## 11. How to Extend the Project

Ideas for future work:

1. **Add a random forest** to `model.py` and compare its MAE to the decision
   tree.
2. **Test day-by-day generalisation**: train on Monday–Wednesday, test on
   Thursday and Friday separately.
3. **Add counter-level balking**: cap the counter queue to reflect students
   who switch counters or leave when a specific counter is very long.
4. **Add a scenario experiment**: simulate adding one server at Supreme BBQ
   during the lunch rush and measure the effect on the peak counter queue.
5. **Widen the arrival tail**: replace the Gaussian arrival spread with a
   longer-tailed distribution to better capture the observed 20–30 minute
   student trickle-out after a lecture.
